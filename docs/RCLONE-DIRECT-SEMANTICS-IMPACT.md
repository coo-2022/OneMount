# rclone 直连文件系统语义缺失：实际影响

范围：OneMount 的 rclone cmount + VFS full 直连模式。本地后端的 WinFsp 测试和 rclone v1.75.0 源码是当前证据；不能把结果推广成所有网盘、所有 Windows 应用均已验证。

核心判断：普通文件数据读写可用，不等于完整实现 NTFS。缺失语义可能表现为明确报错、调用成功但元数据未生效，或者保护条件失效；这三种影响需要分别处理。54 个失败不是 54 个独立缺陷，很多由同一个未实现能力引起。

## 按实际后果分析

| 能力或问题 | 已观察/源码确认的行为 | 对用户和应用的影响 | 优先级与边界 |
|---|---|---|---|
| 执行权限 | 默认 0666 导致启动挂载盘上的测试程序被拒绝 | 能读到 EXE，却无法运行；安装器、便携软件和部分开发工具受影响 | 本轮将文件权限设为 0777，[六项 Windows 回归已通过](RCLONE-DIRECT-FIXES-2026-10-10.md)；不表示所有安装器已验证 |
| 重复创建目录 | 已存在的目录再次创建仍返回成功 | 检测目录是否被占用的逻辑出错；将“成功建目录”当作抢占锁的程序可能让多个执行者都认为获锁 | 本轮在 cmount 边界修正，并验证同一实例并发创建只有一个成功；不提供跨挂载/云端外部写入者的原子保证 |
| 只读、隐藏、归档属性 | 未实现完整属性保存/查询；只读目标在测试中仍可被覆盖 | 文件保护失效导致误覆盖；依赖隐藏/归档位的显示、备份或管理流程可能不符合预期 | 高优先级。不能仅在 UI 显示“只读”而后端不执行保护；隐藏位也不是权限隔离 |
| Windows ACL | 统一 POSIX 权限映射，Chmod/Chown 返回成功但不保存任意 DACL | Windows“安全”界面的修改不一定生效；应用创建的受限文件/目录不能按 NTFS 的细粒度规则隔离 | 高优先级。不要以挂载盘的逐文件 ACL 承诺多用户隔离；它与网盘账号授权、令牌保护是不同层次 |
| 创建时间、访问时间 | cmount 主要使用 ModTime，Utimens 仅保存修改时间 | 文件按创建时间排序、元数据恢复、依赖访问时间的清理策略可能错误；迁移后无法保证三种时间分别保真 | 中优先级。修改时间路径仍存在，不能因此断言所有按 mtime 的增量备份都会失败 |
| ADS 命名流 | 当前 WinFsp FUSE 层关闭 NamedStreams，冒号流路径被拒绝 | 带 ADS 的 NTFS 文件无法保证完整复制；应用可能报错或只复制主数据流。Zone.Identifier 等也是 ADS，可能无法保留 | 需明确能力边界。丢失 ADS 不等于主文件字节损坏；是否提示/忽略由具体复制工具决定 |
| 符号链接、其他重解析点 | 链接默认关闭，任意 GUID/NFS 重解析点不受支持 | 包管理器、链接式依赖、带链接的代码仓库、部分同步/备份恢复流程可能失败 | 中高优先级。启用 links 可覆盖部分符号链接场景，但不等于支持所有 junction、重解析点或硬链接 |
| EA 扩展属性 | xattr 操作返回 ENOSYS | 依赖 EA 保存附属元数据的应用/迁移工具无法完整工作 | 按目标应用确定优先级；普通不使用 EA 的文档读写不因此必然失败 |
| 独立预分配 | AllocationSize 主要按文件大小取整，不保留独立空间预留 | 应用无法靠预分配确保后续写入有空间；性能、碎片化和空间不足出现的时机可能与本地盘不同 | 不应把这一项直接解读为数据已损坏，也不能用改返回值伪造已预留空间 |
| 命名流目录通知 | 测试线程等待流通知，90 秒超时 | 依赖流变化通知的程序可能等待或不刷新 | 当前证据仅针对流通知；普通目录通知测试通过，不能扩大为“所有文件监控均不可用” |
| 删除后可见性、WSL stat | 前者在 NTFS 对照也有相同旧预期差异；后者返回状态尚需定点确认 | 特定应用如果依赖对应错误码/信息类可能不兼容 | 区分兼容性差异与数据损坏，不因用例名含 WSL 就宣称全部 WSL 无法使用 |

## 另一个更关键的边界：写成功不等于远端持久化

源代码 `cmd/cmount/fs.go` 的 `Fsync` 是直接返回成功的空实现；OneMount 直连使用 VFS full 和 5 秒写回延迟。因此，应用写入/关闭文件或发起同步请求，不能单独证明文件已经成功上传到网盘。上传完成还依赖队列排空、网络与后端成功确认。

正常安全卸载会检查上传状态，但强制结束、设备故障、丢失或清理尚未上传的本地缓存属于另外的恢复问题。读写测试、文件锁测试和 FSX 通过，都不能自动证明远端断电一致性或数据库事务持久性。不要将全部文件系统测试“通过率”当作可靠性或持久性百分比。

这一点不是本轮新发现的文件内容损坏，而是调用语义和远端确认之间的边界。此处依据是实际挂载参数及固定版本源码，不是对任何网盘服务作可靠性保证。

## 对 OneMount 当前用途的判断

- **文档、图片、视频、模型权重等普通文件的读取和管理**：与当前能力较匹配；仍需验证目标网盘并确认待上传队列已清空。
- **Agent 轨迹归档**：优先写入本地，再归档到网盘；将上传完成作为远端可用状态。若轨迹使用 JSONL 等普通文件，注意结束写入与上传完成不是同一事件。
- **程序安装、开发工作区、依赖管理**：执行权限修复只是第一步，还会遇到链接、只读属性、时间戳等差异。应按具体工具验收，不能只看 EXE 能启动。
- **数据库、虚拟机磁盘、要求事务持久性的 Agent 状态库**：目前不足以承诺本地 NTFS 等价语义。优先让本地可靠存储承担实时写入，直连盘用于经过应用一致性处理的备份或归档；不要直接把运行中的数据库目录当作普通文件同步即可得到一致备份。

## 处理顺序

1. 本轮执行权限和独占 mkdir 修复已完成 Windows 回归；六项由失败变为通过，原先通过项没有退步。
2. 优先补只读保护，再决定属性/时间/ACL 元数据如何持久化并跨重挂载保留。
3. 对链接、ADS、EA 等能力给出明确支持范围，并按目标应用增加验收。
4. 持久化与恢复单独测试：异常退出、缓存恢复、上传失败重试、清理保护、跨客户端行为。它们不能由现有 117 项完全替代。
