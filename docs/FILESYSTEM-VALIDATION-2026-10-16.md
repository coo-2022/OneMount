### 应用及数据完整性

NTFS、JuiceFS 同步、JuiceFS 后台三个目标均完成以下独立检查：

- 128 MiB 实体文件、32 个 JuiceFS 数据块，跨块随机覆盖；预期哈希由独立确定性数据模型计算。
- 5 GiB 稀疏逻辑长度、超过 4 GiB 偏移的写入及零洞检查。
- 1000 个中文文件、50 个目录、24 层深目录。
- 隔离 Git 仓库的初始化、两次提交、`git fsck`，以及模拟编辑器的临时文件替换保存。
- 两种 JuiceFS 模式安全卸载、移走本轮读缓存后重挂载：**1002 个文件的长度/哈希、稀疏区域和删除结果一致**。
  NTFS 对照执行普通重读；Git 完整性检查是在冷重挂载之前执行。

三写进程同时替换同一个文件的严格场景，在三个目标均出现 `EPERM`。
该场景仍计失败，不能单独归因于 JuiceFS，也未通过添加重试来消除失败。
初次运行停在此处；随后仅继续尚未执行的 Git 和冷读阶段，保留原始失败报告。
这尚不能证明共享访问、锁、截断组合或真实 Office/编辑器工作流全部兼容。

使用独立 SQLite、独立缓存、仅绑定回环地址的故障代理与本地 rclone S3 网关，

| 故障 | 观察到的注入 | 恢复结果 |
